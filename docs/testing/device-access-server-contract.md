# HWID и отзыв WDTT: инструкции для серверной части

Клиент: iOS vipin, схема `VKTurnPrototype`. Дата: 28 октября 2026 года.

Изменения клиента выполнены в `sing-prototype`. В `/Users/acurofobia/code/VPN` и на `ssh panel` / `ssh wdtt2` в рамках реализации ничего не менялось. Ниже — контракт, который необходимо реализовать на сервере.

## 1. Границы ответственности

Для новых приложений с capability `device-access-v1` кастомный backend ведёт реестр WDTT-устройств с лимитом **2 допущенных устройства на внутренний аккаунт пользователя** по умолчанию. Старые приложения продолжают работать с WDTT по прежним правилам до перехода на новое приложение (см. раздел 2.1). Remnawave независимо проверяет доступ к VLESS. Исходный HWID клиента передаётся в Remnawave без подмены.

После получения отзыва при обновлении подписки клиент удаляет WDTT-ключ из сохранённой подписки и runtime Keychain, блокирует повторный запуск и останавливает WDTT-туннель. VLESS-конфигурация сохраняется. Выключенное устройство или устройство без связи применит отзыв при следующем успешном обновлении подписки.

Это удаление ключа штатным приложением. Если пароль ранее скопировали в сторонний клиент, отключение лимитов в WDTT позволит продолжить его использование. Для гарантированного серверного отзыва потребуются отдельные реквизиты на устройство или проверка допуска при подключении к WDTT.

## 2. Заголовки клиента

Манифест, конфигурация, UI на том же origin получают:

```http
User-Agent: VipinApp/1.0 (iOS)
X-Subscription-Format: vipin-v1
X-Subscription-Capabilities: vless-failover-v1 device-access-v1
x-hwid: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
x-device-os: iOS
x-ver-os: 27.0.0
x-device-model: iPhone14,5
```

Capabilities — список токенов через пробел. Проверять наличие `device-access-v1` / `vless-failover-v1`, а не равенство всей строки одному значению. Модель устройства — аппаратный код, без имени, заданного пользователем.

### 2.1. Совместимость старых и новых приложений

- Запросы без capability `device-access-v1` обслуживать по существующему протоколу: сохранить текущий формат манифеста, выдачу WDTT-ключа, конфигурации и UI по прежним правилам подписки и тарифа. Отсутствие нового HWID или допуска в новом реестре не должно блокировать WDTT старых приложений. Такие запросы не регистрируют устройства в новом реестре и не занимают его слоты.
- Запросы с capability `device-access-v1` обрабатывать по новому протоколу: проверять HWID и допуск, применять лимит устройств и возвращать `device_access`. При невалидном или отсутствующем HWID не переключать такой запрос на старый протокол. Эти правила применяются к манифесту, config и UI с сохранением независимости VLESS и WDTT.
- При переходе пользователя на новое приложение регистрировать его HWID по новым правилам. Переход, отказ новому устройству или отзыв отдельного HWID не должны менять общий WDTT-пароль, деактивировать общий аккаунт либо отключать оставшиеся старые приложения. Проверки подписки и тарифа сохраняются для обоих протоколов.
- Наличие capability определяет протокол, но не доказывает версию или подлинность клиента. Пока старый протокол поддерживается, новый лимит и отзыв не гарантируют ограничения всех способов получения и использования общего WDTT-ключа.

### 2.2. Авторизация и HWID нового протокола

Следующие требования к допуску и обязательному HWID относятся к запросам с capability `device-access-v1`.

Первичный манифест запрашивается без Bearer. Для config и UI используется существующий `Authorization: Bearer <ui_token>`. Этот токен не заменяет проверку HWID: нельзя считать любой запрос с токеном допущенным устройством.

Принимать ровно один `x-hwid`, соответствующий `^[a-zA-Z0-9=-]{10,64}$`. iOS выдаёт 64 строчные hex-цифры, созданные из случайного значения и сохранённые в общей Keychain без синхронизации iCloud и переноса на другой аппарат. Не менять регистр и не преобразовывать HWID. При отсутствующем/невалидном HWID не выдавать WDTT-ключ, не использовать общую заглушку и не подменять идентификатор ссылкой подписки.

## 3. Расширение манифеста кастомной подписки

Для клиента с capability `device-access-v1` сохранить текущие поля и заголовок ответа `X-Subscription-Format: vipin-v1`, добавить `device_access`:

```json
{
  "sing_box_url": "https://sub.example.com/api/sub/KEY/app/v1/config",
  "ui_url": "https://sub.example.com/api/sub/KEY/app/v1/ui",
  "ui_token": "existing_signed_token_here",
  "vk_turn_link": "wdtt://existing-user-specific-link",
  "device_access": {
    "schemaVersion": 1,
    "hwid": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "state": "allowed",
    "revision": 1
  }
}
```

При отказе вернуть `vk_turn_link: null`, валидные UI/VLESS URL и явное решение в `device_access`. Не создавать/реактивировать WDTT-аккаунт и VK-вызов для отклонённого устройства.

Клиент применяет валидное решение по устройству при загрузке манифеста, до разбора остальных полей и загрузки VLESS/UI. Ошибка другого режима не должна предотвращать удаление отозванного ключа. Устаревший ответ без `device_access` не отменяет ранее сохранённый отказ.

## 4. Решение о доступе в манифесте

Отдельный endpoint не нужен. Объект `device_access` содержит только `schemaVersion`, `hwid`, `state` и `revision` (не более 16 KiB). Дополнительные URL/токены проверки не требуются.

| state | Поведение WDTT и сообщение клиента |
| --- | --- |
| `allowed` | Выдать ключ в `vk_turn_link`, если у устройства есть допуск и тариф. |
| `device_revoked` | Удалить ключ и остановить WDTT. «Доступ для этого устройства отозван». |
| `device_limit_reached` | Не выдавать ключ; удалить ранее сохранённый, если он есть. «Лимит устройств исчерпан». |
| `not_allowed` | Нет допуска к WDTT. Удалить ключ и остановить WDTT. «Обход белых списков недоступен для этого устройства». |

Отозванная запись всегда возвращает `device_revoked`, даже если освободился слот. При заполненном лимите новый HWID получает `device_limit_reached`. Не обозначать отзыв только HTTP 403/404: вернуть обычный манифест HTTP 200 с явным решением и без WDTT-ключа.

Неизвестные state, чужой HWID в ответе, ошибочный JSON, HTTP-ошибки и таймауты не считаются изменением допуска. Они не удаляют разрешённый ключ и не восстанавливают отозванный.

`revision` — неотрицательное целое в диапазоне Int64, монотонное для данной подписки и HWID. Увеличивать при изменении состояния, включая восстановление доступа и изменение права по тарифу. Одна ревизия всегда означает одно и то же решение целиком. Старый ответ не перезаписывает более новый; конфликтующие решения одинаковой ревизии отклоняются.

Ревизии хранить в БД. Не обнулять их при удалении устройства, перезапуске worker или восстановлении тарифа. Откат БД на ревизии ниже уже выданных требует отдельного восстановления согласованности, а не сброса HWID клиента.

Возврат доступа: явно разрешить устройство с учётом лимита, увеличить ревизию и выдать новый манифест с ключом при следующем обновлении подписки.

Персональные ответы: `Cache-Control: no-store`. Отключить кэширование манифестов в reverse proxy/CDN. Нельзя разделять кэш между HWID. Полные URL подписок, токены, HWID и WDTT-ссылки не должны попадать в журналы.

## 5. Что изменить в backend `/Users/acurofobia/code/VPN`

Проверки нового реестра и изменения манифеста/UI ниже применять к протоколу `device-access-v1`; обслуживание старых приложений сохранить согласно разделу 2.1.

1. Добавить таблицу устройств с уникальностью `(user_id, hwid)` либо индексируемым keyed hash идентификатора. Хранить платформу/модель, даты регистрации и последнего обращения, состояние допуска и ревизию. Привязка — к постоянному внутреннему user ID, не к shortUuid или WDTT-паролю. Считать допущенные устройства; отклонённые попытки слоты не занимают.
2. Добавить лимит 2 по умолчанию с индивидуальными исключениями. Существующие лимиты WDTT-панели не становятся автоматически бизнес-лимитами backend. До миграции решить, что делать с текущими исключениями.
3. На запросе манифеста проверить подписку и право на WDTT, затем атомарно найти существующий допуск или занять свободный слот. Учитывать конкурирующие запросы и несколько workers. `asyncio.Lock` и незащищённые `COUNT` → `INSERT` недостаточны. Не держать DB lock во время вызовов WDTT/VK; при необходимости использовать ограниченное по времени резервирование с идемпотентным повтором.
4. В `backend/app/subscriptions/service.py` проверять допуск до `ensure_app_connection`. Отказ должен происходить до удалённого provisioning. После сетевой операции повторно проверить право/тариф перед выдачей ключа. Третье устройство не должно деактивировать общий WDTT-аккаунт первых двух.
5. UI-запрос должен отражать допуск именно текущего HWID и не регистрировать устройство. Согласовать отсутствие `vk_turn_link` с состоянием режима. Различать лимит, отзыв, отсутствие тарифа и временную недоступность панели.
6. В `backend/app/subscriptions/ui.py` для отказа устройства возвращать `option02.state = unavailable` и понятный `stateText`. `option01` оставить под управлением правил VLESS. Клиент дополнительно накладывает сохранённый отказ WDTT, поэтому устаревший UI не сможет повторно включить этот режим.
7. Добавить авторизованные действия списка устройств, отзыва и повторного допуска. Отзыв освобождает слот, но сохраняет tombstone и ревизию. Повторный отзыв идемпотентен. Обновления/повторные импорты не должны автоматически регистрировать отозванный HWID. Ограничить частоту регистраций и административных замен устройств.
8. Убрать показ, копирование и экспорт сырого WDTT-ключа из бота и связанного личного кабинета. Вместо выдачи ключа добавить управление устройствами нового реестра: список, отзыв и повторный допуск через авторизованные действия из пункта 7, с отображением состояния и лимита. Браузерная сессия или открытие бота не являются HWID VPN-устройства и не регистрируют устройство. Проверить все пути выдачи ключа: `/wdtt/users/{id}/status`, `/connect`, экспорты ссылок и личный кабинет; исключить выдачу сырого ключа через бот/кабинет, сохранив необходимые старым приложениям ответы сервера подписок согласно разделу 2.1. Удаление ключа из бота не должно менять пароль или отключать уже настроенные приложения.
9. Согласовать счётчики и существующие сбросы. Текущий список HWID берётся из Remnawave, отвязка WDTT очищает привязки её панели — новый реестр они не обновляют. Перевыпуск ссылки подписки не должен незаметно обнулять список устройств.

## 6. Передача HWID в Remnawave

`backend/app/subscriptions/remna_subscription.py` уже пересылает `user-agent`, `x-hwid`, `x-device-os`, `x-ver-os`, `x-device-model`. Сохранить точные значения клиента на каждом upstream-запросе и существующий запрет пересылки клиентского Bearer/cookies в Remnawave. Не регистрировать устройства от имени backend.

До разбора upstream-конфига обработать `x-hwid-not-supported`, `x-hwid-max-devices-reached` и старый `x-hwid-limit`. Перевести отказ в недоступность **только VLESS**. Не превращать его в общий отказ подписки, который мешает отзыву или работе WDTT.

Текущий клиентский decoder VLESS принимает причины `not_allowed` / `traffic_limited`: для отказа по HWID использовать `not_allowed`, а подробную причину показать в UI.

При исследовании на `panel` обнаружена Remnawave 2.6.4. Проверить поведение именно установленной версии и настройки External Squad. Допуск в одном реестре не гарантирует допуск в другом: этот дизайн оставляет WDTT и VLESS независимыми.

## 7. Изменения WDTT и порядок включения

Сначала внедрить backend с совместимостью из раздела 2.1, убрать выдачу ключа из бота/кабинета, добавить управление устройствами и протестировать совместную работу старых и новых приложений. Только затем ослаблять ограничения WDTT для выбранных аккаунтов. Не менять общий WDTT-пароль и не отключать старые приложения в рамках внедрения; ранее выданные ключи продолжают работать по прежним правилам подписки и тарифа.

- Подтвердить способ отключения лимита установленного WDTT. В опубликованном `server/devices.go` значение `max_devices <= 0` означает лимит по умолчанию, а не unlimited.
- `backend/app/wdtt/service.py` сейчас создаёт пользователей с `max_devices=1`.
- `backend/app/utils/wdtt_client.py` при обновлении заменяет нулевой лимит на 1. Это не должно отменять выбранные настройки панели.
- Не раздавать главный WDTT-пароль как unlimited-доступ.
- Существующие transport device ID WDTT отличаются от нового HTTP HWID приложения. Не считать их одинаковыми при миграции и не менять transport ID в рамках этого внедрения.
- Сохранить включение/выключение аккаунтов, оплату, лимиты трафика и скорости. Ослабление device limit не отменяет проверку тарифа.

## 8. Поведение клиента и приёмка

Допуск проверяется сервером только при обычном обновлении подписки. Нет минутного опроса, отдельной сетевой проверки перед подключением или фонового мониторинга в VPN-расширении. Полное автообновление по-прежнему ограничено одним разом в час, пока приложение открыто; кнопка «Обновить» запускает его вручную без ожидания интервала.

До получения обновлённого манифеста устройство может пользоваться сохранённым WDTT-ключом. Если приложение свёрнуто или нет связи, удаление откладывается до обновления. После получения отзыва приложение удаляет ключ и останавливает активный WDTT-туннель. Уже полученный отказ сохраняется локально и не позволяет восстановить старый ключ из кэша.

Клиент хранит решения отдельно от манифеста, сериализует запись snapshot и изменение runtime-ключа между процессами. Отзыв не может быть отменён старым ответом, поздней записью snapshot или сменой подписок. При сбросе сохраняются HWID и локальные отметки решений по хешу URL; сами конфигурации и токены удаляются. Повторное разрешение должно прийти от сервера с большей ревизией.

Обязательные проверки на staging:

- Старое приложение без `device-access-v1` продолжает получать прежний манифест, конфигурацию и UI и подключаться к WDTT; отсутствие нового HWID и заполненный новый реестр не блокируют его. Его запросы не занимают слоты нового реестра.
- Новое приложение с `device-access-v1` использует новый реестр; отсутствие или невалидность HWID не позволяют получить WDTT-ключ через переключение на старый протокол.
- Переход одного устройства на новое приложение, отказ третьему устройству и отзыв HWID не отключают старые приложения того же пользователя и не меняют общий WDTT-пароль.
- В боте/кабинете нет показа, копирования или экспорта сырого WDTT-ключа. Список устройств, отзыв и повторный допуск доступны только владельцу аккаунта; открытие управления не занимает слот. Уже настроенные старые приложения продолжают работать.
- Два устройства занимают по одному слоту; повторные импорты и UI-запросы не увеличивают счётчик.
- Третье устройство не получает WDTT-ключ и видит сообщение о лимите. Разрешённый VLESS продолжает работать.
- Отозвать A при подключённом WDTT: до обновления ключ остаётся доступным. Обновить подписку в приложении: ключ удаляется и WDTT останавливается.
- Отключить сеть, отозвать доступ, вернуть сеть: ключ удаляется после успешного получения отзыва при обновлении подписки. HTTP 500, таймаут и ошибочный JSON не должны удалять разрешённый ключ или восстанавливать отозванный.
- Получить отзыв, затем сломать URL/загрузку VLESS или UI: WDTT-ключ всё равно удалён.
- Одновременно доставить старый `allowed` и новый отзыв, записать старый snapshot после отзыва: новый отказ побеждает.
- Сбросить/повторно импортировать подписку отозванного HWID: автоматического допуска нет. Административно разрешить его с новой ревизией и обновить полную подписку: ключ снова появляется.
- Одновременно зарегистрировать два устройства в один оставшийся слот: допустить ровно одно.
- Проверить стабильность HWID после перезапуска, обновления и сброса настроек; на двух физических устройствах ID различаются. Сохранение после переустановки iOS — best effort, не гарантия ОС.

Остановку реального VPN после обновления подписки и совместную работу с панелями нужно проверить после реализации серверной части. Симулятор не заменяет эту проверку.
